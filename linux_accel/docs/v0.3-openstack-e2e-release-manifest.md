## Dynamic DNS/gRPC smoke and Neutron reachability

The two reused Ubuntu instances share security group
`b19f46b5-e78e-4f3f-a8bb-72bc88955c0b`. At collection it allowed SSH and UDP
DNS but did not allow `TCP/50052`, which is the client-proxy to server-proxy
gRPC leg. A controlled reachability probe timed out before that ingress rule
was present and connected immediately after adding a source-restricted
`10.0.0.43/32 -> TCP/50052` rule. The campaign now has an opt-in managed-rule
mode: `MANAGE_GRPC_SECURITY_GROUP_RULE=1` plus
`OPENSTACK_GRPC_BACKEND_SECURITY_GROUP_ID` creates exactly that rule, records
its ID, and deletes and rechecks it during cleanup. The default remains `0`;
normal callers do not receive an implicit security-group mutation.

The corrected script was smoke-tested with the current client tap and
`REQUIRE_NETMIG_TC=1`:

| Smoke | Artifact | Result |
| --- | --- | --- |
| Dynamic decision path | `/tmp/vnet-p0-dynamic-sg-20260730-1300/dynamic-smoke-status-debug` | Three `hot-key` windows: DNS `120/120`, gRPC `120/120`, zero failures, `BYPASS` epoch `1` published `SERVER_CACHE` epoch `2` for the next window; `cleanup_status=0`, no run-owned residue. |
| Server-cache data path | `/tmp/vnet-p0-dynamic-sg-20260730-1300/server-cache-smoke` | One `hot-key` window: DNS `40/40`, gRPC `40/40`, backend requests `0`, DNS server-cache hits `48`, gRPC server-cache hits `48`; `cleanup_status=0`, no run-owned residue. |

## Lifecycle isolation and cleanup

- `RUN_TOKEN` is sanitized and names the guest directory
  `/tmp/vnet-dns-e2e-<token>`; binaries, logs, count files, and PID records
  live below it.
- Test-owned monitor and helper processes start in a private `setsid` process
  group. Cleanup validates PID, process group, session, start time where
  applicable, and the private run directory before signaling it.
- Dynamic-cache, existing-pair, and migration-probe campaigns use the same
  principle: per-run guest directories, isolated BPF pin roots where used, no
  `killall`, and no shared fixed guest artifact names. The dynamic campaign
  also serializes a shared host tap with `flock` and appends a non-reusable
  nonce even when a caller repeats `RUN_TOKEN`.
- Static regression `tests/openstack_campaign_lifecycle_test.sh` rejects
  legacy shared paths, shared pin roots, `killall`, and missing dynamic lock /
  identity markers in all four campaigns. It also requires the dynamic
  campaign's opt-in gRPC security-rule create/delete markers and per-window
  child-status artifact. It is source-level coverage, not
  evidence of a live OpenStack lifecycle or foreign-hook preservation run.
- The formal run reported `cleanup_status=0`. Follow-up inspection found no
  client/backend run directory, token process, or token BPF pin. The client
  tap retained only foreign NetMig TC `0x65/0x66`; no DNS/gRPC test hook or
  XDP attachment remained.
- The run's temporary TCP/22 rule
  `2a786517-ec5e-423e-9198-4c83c49e4f5d` and the separate post-check rule
  `092d842f-5377-4187-8864-c629b4f16c68` were both verified absent. Both
  reused instances remained `ACTIVE`.

## Boundaries carried into P1

- The dynamic DNS/gRPC campaign's three-endpoint map write is serial
  experiment orchestration, not distributed atomic epoch publication.
- DNS XDP cleanup uses an atomic `old_prog_fd` precondition. Legacy
  `bpf_tc_*` detach remains slot-based, so its readback guard is fail-closed
  for observed ownership changes but cannot make an uncoordinated external
  replacement race atomic. P1 should add TCX BPF-link lifecycle where
  supported, with an explicit `BYPASS` fallback.
- The current Agent is a manual, single-port `watch` workflow. systemd,
  multi-port state/health reporting, migration freeze/recovery, and
  health-gated epoch publication are P1 acceptance work.
- gRPC fast response remains a userspace service path; this release does not
  claim universal in-kernel TCP/HTTP2 response synthesis.
